# Лекция 2 — Архитектура baseline: от Docker до агентного цикла

## Ключевые темы

- Полная архитектура pipeline стримерши
- Система фильтрации входящих и исходящих сообщений (регулярные выражения + нейронные фильтры)
- Java-часть проекта: структура мода, система задач (chains), Py4J Entry Point
- Python-часть: MindBridge, цикл событий (KTX Swarm), промпт-конструктор
- Система инструментов (tools) агента: speak, yandere mode, minecraft commands
- Промпты и файл personalities.yml
- Смарт-триггеры для автономных агентов
- LiteLLM для смены моделей
- Сравнение агентных фреймворков: LangChain, LangGraph, SmolAgents vs собственная реализация

## Теория

### Общая архитектура pipeline

Для запуска стримерши необходимо поднять несколько компонентов:
1. **Docker-контейнеры** — в папке `docker/` лежит docker-compose, который поднимает два контейнера: фильтр (фильтрация сообщений) и TTS (Fish Speech)
2. **Minecraft** с модом AltaClev
3. **Python-скрипт** — основная логика агента
4. **OBS / YouTube Studio** — для ведения трансляции

Порядок запуска: сначала Docker (TTS + фильтр), затем Minecraft, потом Python-скрипт.

### Система фильтрации сообщений

Двухуровневая фильтрация:

**Первый уровень — регулярные выражения (regex).** Фильтрует по корням слов (не по полным словам), чтобы учесть склонения и словоформы. Используются regex-паттерны для блокировки вариаций нежелательных слов. Прямое вхождение (без regex) используется для жёстких блоков: фамилии политиков, религиозная тематика. Если корень слова совпадает — сообщение блокируется полностью.

**Второй уровень — нейронные фильтры.** Более медленный, но контекстно-зависимый. Оценивает токсичность сообщения по шкале (score). Обычный мат без токсичного контекста (score < 10) пропускается. Токсичный контекст (оскорбления меньшинств и т.д.) блокируется.

**Двусторонняя фильтрация:** фильтруются и входящие сообщения (от игроков), и выходные (от LLM). Принцип garbage in → garbage out: если не почистить вход, LLM начнёт генерировать мат и нежелательный контент.

Наборы фильтров конфигурируемы: Twitch-набор блокирует оскорбления меньшинств, политику, религию. Обычный мат — пропускается (опционально).

### Java-часть проекта (мод AltaClev)

Проект на Java — объектно-ориентированный, каждая папка = модуль/пакет, внутри — классы.

**Система задач (chains/tasks):** иерархическая. Каждая задача может содержать подзадачи. Пример: команда `game speedrun` → KillPlayerTask → подзадачи поиска и атаки. Команда `strike nick` транслируется в PunkCommand → KillPlayerTask.

**Py4J Entry Point** — входная точка, связывающая Java и Python. Здесь прописаны все методы-мосты: пересылка чат-сообщений в Python, пересылка игровых событий (onDeath, onKill, onDamage). Используются Python-коллбэки: когда в игре происходит событие, Java вызывает соответствующий метод в Python.

**Определение смерти игрока** реализовано костылём: мод отслеживает HP каждого игрока. Если HP упало до 0 или резко стало 20 (игрок возродился) — считается, что игрок умер. Прямого API для этого в Minecraft нет (код залочен разработчиками). Миксины не решают эту проблему; через сетевые пакеты — уже читы.

**Запуск Java-части для разработки:** клонировать репозиторий, открыть в VS Code (он подскажет нужные расширения для Java), запустить `gradle runClient`. Изменения вносятся в код → снова `gradle runClient`.

### MindBridge — сборщик данных

MindBridge — модуль в Python-части (DataCollector), который собирает все данные из Minecraft и конвертирует их в текстовый формат для цикла событий агента. Источники данных:

1. **Голосовые пакеты** — от voice chat, с привязкой к нику игрока (агент знает, кто говорит)
2. **Серверные сообщения** — broadcast-сообщения сервера (менее приоритетны)
3. **Сообщения игроков** — парсятся из чата с определением ника; парсер в Java-части, Python получает готовую структуру {ник: сообщение}
4. **ЛС в Minecraft** — личные сообщения, отдельный формат парсинга
5. **Игровые события** — смерть, убийство, урон → конвертируются в текст: «игрок X убит игроком Y»
6. **Сообщения с Twitch/YouTube/Discord** — тоже попадают в общий цикл событий

Все данные конвертируются в единый текстовый формат и попадают в цикл событий (KTX Swarm).

Важно: парсинг чата зависит от конкретного сервера. На незнакомом сервере агент может не понимать сообщения. В мод-конфиге есть настройки под разные сервера для кастомизации парсинга.

### Цикл событий (KTX Swarm)

KTX Swarm — структура, хранящая последние 100 объектов событий. Не все из них попадают в промпт — промпт-конструктор выбирает релевантные. Это основа контекста агента: он «видит» историю событий и на её основе принимает решения.

### Промпты и файл personalities.yml

Промпты хранятся в `resources/personalities.yml`. Здесь описываются роли агента — это системный промпт для LLM.

Ключевые правила написания промптов для автономного агента:
- Жёстко управлять вниманием модели (указывать, на что обращать внимание, на что нет)
- Несколько раз повторять критичные инструкции (LLM может «забыть» при длинном контексте)
- Примеры ответов — полезны, но LLM склонны их копировать дословно; нужно явно и многократно указать, что это ТОЛЬКО пример, не финальный ответ
- В .env файле необходимо заменить ник на свой

### Система инструментов (tools)

Инструменты — Python-функции в папке `agent_tools/`. Комментарии (docstrings) копируются агенту как описание инструмента. Название функции = название инструмента для агента. Описание в коде критично — оно прямо попадает в промпт.

**Базовые инструменты:**
- `speak(comment, emotion)` — сказать что-то (отправляет в TTS + чат Minecraft одновременно). Эмоция влияет на озвучку
- `enter_yandere_mode` — переключение личности на «яндере-режим» (смена промпта). Вызывается через `!enter_yandere_mode` или через эмоцию «yandere» в speak
- `minecraft_command` — выполнение команд в Minecraft (spawn, punch nick и т.д.)

**Tool Status** — механизм динамического описания инструментов. Метод `{tool_name}_tool_status()` вызывается при каждой сборке промпта и возвращает текущий контекст (например, на каком сервере агент, какие команды доступны). Есть база серверов с описаниями команд под каждый.

### Смарт-триггеры

Проблема простого цикла (запуск LLM каждые 10 секунд): огромные задержки. Если агента убили сразу после очередного запуска — он отреагирует только через 10+ секунд ожидания + 3-10 секунд генерации = 20+ секунд задержки.

**Решение — smart triggers.** Базовое ожидание ~10-15 секунд, но с приоритетными триггерами:
- Сообщение в чате (особенно с упоминанием ника агента) → немедленный запуск
- Смерть агента → немедленный запуск
- Убийство игрока → немедленный запуск
- Урон → триггер

При срабатывании триггера агент получает в промпте информацию о вызвавшем событии: «произошло такое-то событие, отреагируй прямо сейчас». Без триггера: «никаких событий не произошло». Это ключевой механизм, обеспечивающий релевантную и быструю реакцию агента.

Управление триггерами находится в reaction-агенте / planner-агенте.

### LiteLLM для смены моделей

Используется LiteLLM через LangChain. Позволяет менять LLM-провайдера без изменения кода — достаточно изменить строку model_name в .env. Примеры: `openai/gpt-4`, `mistral/mistral-small-3.2`. Для каждого провайдера нужен соответствующий API-ключ в .env.

### Почему не LangChain / LangGraph / SmolAgents

**LangChain (агентная часть):** сложно парсить tool_calls, тяжело залезть во внутренности цикла агента. Для кастомизации промптов и формата инструментов — пытка. Нужно много патчей.

**LangGraph:** ещё хуже — огромное количество бойлерплейт-кода для минимального функционала. Тяжело получить доступ к внутренностям, изменить параметры тулов.

**SmolAgents (Hugging Face):** интересная идея — агент вызывает инструменты как Python-код (функции с параметрами). Но LLM начинают писать слишком сложный код (циклы, новые функции на 100 строк) вместо простого вызова инструментов. Нужен fine-tuning, а если fine-tuning — лучше сразу на командный формат.

**Вывод:** для автономного агента с бесконечным циклом (while true) все существующие фреймворки не подходят. Они заточены под задачу с конечным результатом. Проще написать свой pipeline: класс агента с методом run (while true), prompt-конструктор, парсер, вызов инструментов.

## Практика

### Запуск Docker-контейнеров

В папке `docker/filter/` запустить docker-compose — поднимутся контейнеры с фильтром и TTS (Fish Speech). TTS принимает HTTP-запросы от Python-скрипта и возвращает аудиофайлы.

### Работа с Java-частью

1. Клонировать репозиторий мода
2. Открыть в VS Code (установятся Java-расширения)
3. `cd ваш_проект && gradle runClient` — запуск Minecraft с модом
4. Для изменения поведения — редактировать Java-классы (например, KillPlayerTask) → пересобрать через `gradle runClient`
5. Copilot/Claude Code помогут с Java-кодом

### Настройка промптов

1. Открыть `resources/personalities.yml`
2. Заменить описание персонажа на своё
3. В `.env` заменить ник на свой
4. При написании примеров ответов — явно указать «это ПРИМЕР, не копировать дословно» (минимум 3-5 раз)

### Смена LLM

В `.env` изменить переменную с названием модели: `model_name=mistral/mistral-small-3.2`. Добавить API-ключ провайдера. Перезапустить Python-скрипт.

## Инструменты и технологии

- **Docker / docker-compose** — контейнеризация TTS и фильтра
- **Fish Speech** — TTS-система, работает как HTTP-сервер в Docker; принимает текст + референс голоса → возвращает аудио
- **Py4J** — Java↔Python мост через сетевое соединение
- **MindBridge** — модуль сбора и конвертации данных из Minecraft (в Python-части, DataCollector)
- **KTX Swarm** — структура цикла событий, хранит последние ~100 объектов
- **LiteLLM** — универсальный клиент для LLM-провайдеров, позволяет менять модель одной строкой
- **LangChain** — используется частично (LiteLLM через LangChain), но не агентная часть
- **SmolAgents (Hugging Face)** — альтернативный агентный фреймворк, не используется в проекте из-за ограничений
- **LangGraph** — граф-агентный фреймворк, не используется из-за избыточности кода
- **Regex** — первый уровень фильтрации сообщений по корням слов
- **Gradle** — система сборки для Java-части проекта

## Ответы на вопросы студентов

**В: Pipeline фильтрации быстро работает?**
О: Regex-часть — быстро. Нейронные фильтры — медленнее, но всё равно быстрее генерации LLM. В сумме задержка от фильтрации незначительна на фоне общего pipeline.

**В: Почему бы не использовать лемматизацию (приведение к начальной форме) вместо regex?**
О: Можно рассмотреть. Но regex решает задачу достаточно хорошо для текущих нужд, а лемматизация добавит зависимость от NLP-библиотек и может замедлить pipeline.

**В: Насколько сильно надо фильтровать выходные сообщения?**
О: Зависит от платформы стриминга. Для Twitch: блокировать оскорбления меньшинств, политику, религию. Обычный мат — по желанию. Для собственной безопасности — блокировать политику и религию всегда.
