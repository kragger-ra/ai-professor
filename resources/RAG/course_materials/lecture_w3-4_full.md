# Конспект лекции — Неделя 3-4

## 1. Общая архитектура автономного ИИ-стримера
- **Baseline-проект**: цифровой персонаж, способный без участия человека играть в Minecraft, вести трансляции, развлекать зрителей, принимать игровые решения и планировать действия в рамках одного прохода.
- **Автономные vs Task-based агенты**: автономные работают в бесконечном цикле (`while True`) без явного завершения задачи, в отличие от классических task-based агентов, вызываемых под конкретную задачу.
- **Модульность и декомпозиция**: компромисс между глубокой интеграцией в одну игру и созданием универсального ядра стримера с подключаемыми игровыми SDK. Рекомендуется выносить тяжелые компоненты (STT, фильтрация) в отдельные Docker-контейнеры и отделять игровую логику от ядра.
- **Оркестрация мультиагентных систем**: планируемая синхронизация узлов (нод) для координации действий, предотвращения спама и хаотичного поведения на сервере.
- **Масштабируемость**: проект можно запускать на нескольких физических ПК или ВМ. Основное ограничение — виртуальные аудиокабели (обычно один на ОС), но обходимо.
- **Архитектурные паттерны**: `Clean Architecture` и `Onion Architecture` признаны избыточно сложными. Для сохранения общей личности и памяти при разделении модулей предлагается `Monorepo`.

## 2. Пайплайн фильтрации и модерации
- **Принцип `Garbage in, garbage out`**: обязательная очистка входных данных перед подачей в LLM для предотвращения токсичного или некорректного вывода.
- **Двойная система фильтрации**: независимая проверка входящих сообщений (от зрителей/игроков) и исходящего текста LLM перед отправкой в эфир/чат.
- **Уровни фильтрации**:
  1. **Правила/Regex**: быстрая проверка по корням слов и шаблонам (нецензурная лексика, фамилии политиков). Работает значительно быстрее нейросетей.
  2. **Нейронные классификаторы**: тематическая классификация (политика, религия) и оценка токсичности. Склонны к ложным срабатываниям на эмоциональные высказывания.
- **Логика принятия решений**: `чувствительная тема + токсичность` → 100% блок. Нейтральная тема + «плохие» корни → проверка порога «скор ошибок». При превышении порога сообщение блокируется.
- **Эмбеддинги vs Классификаторы**: эмбеддинги неточны для задач модерации. В production рекомендуются файн-тюненные классификаторы (например, BERT для бинарной токсичности и мультиклассовой тематики).
- **Развертывание**: фильтр работает в отдельном Docker-контейнере. Запуск опционален для самостоятельного тестирования.

## 3. Интеграция Minecraft и Python (Мосты и данные)
- **Связь Java ↔ Python**: реализуется через `Py4J` (сетевой мост-входная точка для обмена данными).
- **`MineBridge` / `MindBridge`**: кастомные модули-мосты (в `DataCollector`). Пересылают чат, голосовые пакеты и игровые ивенты из Java в Python через callback-механизмы (`onDeath`, `onKill`).
- **Разделение парсинга**: Java-часть отвечает за сырой парсинг чата и извлечение ников/текста. Python получает уже структурированные данные.
- **Детекция смерти**: мониторинг HP. Если HP падает до `≤0` или резко сбрасывается до `20` (респаун), генерируется ивент. Описывается как «костыль» из-за закрытости исходного кода Minecraft.
- **Типы клиентов Minecraft**:
  - *Java-клиент с модами*: стабильный, поддерживает сложных агентов (Baritone, Tungsten), но ресурсоемкий.
  - *MindFlayer (JS-клиент)*: легковесный, проще масштабировать, но нестабилен, часто вылетает и блокируется античитами.
  - *Терминальный клиент (Rust)*: без GUI, рендерит упрощенную графику в терминал или веб (`MindFlayer viewport`). Экономит ресурсы.
- **Серверные ограничения и авторизация**: капча, логин, навигация в лобби, античиты. Современная Microsoft-аутентификация вызывает `Invalid Session` при запуске через моды. Обход: однократный вход через стандартный клиент → подключение терминального клиента под тем же профилем.

## 4. Цикл событий и управление контекстом
- **`KTX Swarm`**: корневая структура для динамических переменных в реальном времени (состояние системы, фильтры, активные ники, очереди). Статические данные задаются в `.env`.
- **`KTX Chat`**: поле внутри `KTX Swarm` (реализуется как список/sequence), куда поступают все события из чатов, голосовых каналов и игровых механик.
- **`EventBase`**: базовое событие (словарь `dict` в Python). Содержит поля: `Yenv` (источник: Minecraft, Twitch), `ProcessingTimeStand` (уникальная метка времени в наносекундах + дата).
- **Поток данных**: `DataCollector` фиксирует событие → итерация по `InternalEvents` → `MainBridge` отслеживает → `Handler` добавляет в общий цикл.
- **Фильтрация контекста**: передача всех событий в LLM невозможна из-за риска переполнения. Применяется жесткое лимитирование с приоритетом сообщений игроков над серверными.
- **`Helper` (формирование промпта)**: делит отфильтрованные данные на 3 временные группы:
  - *Старые*: жесткая фильтрация, остаются только сообщения игроков.
  - *Релевантные*: добавляются важные серверные события (убийства, смерти).
  - *Недавние (~5 сек)*: полная детализация всех событий без фильтрации.
- **Мерджинг сообщений**: близкие по времени сообщения от одного пользователя объединяются в одно, если между ними не было других событий.
- **`UserInfo`**: структура данных об игроке. Поддерживает привязку нескольких ников, агрегирует данные из БД, статистику упоминаний и игровые метрики (HP, режим, позиция, предмет в руках, возможность атаки).
- **`Prompt Constructor`**: собирает `UserInfo`, данные БД, игровые метрики и доступные инструменты в единый промпт для LLM.
- **Пересборка промпта**: происходит при каждом вызове LLM. Изменение промпта во время генерации ответа физически невозможно без стриминг-архитектур трансформеров.

## 5. Промпт-инжиниринг и работа с LLM
- **Жесткое управление вниманием**: четкие ограничения («что делать/не делать»), детальное описание характера, внешности, предпочтений, темперамента.
- **Идентичность**: многократное указание никнейма и связки «ник = ты» для фиксации личности и предотвращения ответов от чужого имени.
- **Примеры ответов**: явно маркировать как `это пример, не то, что нужно писать в чат`, иначе LLM копирует их дословно.
- **Запрет на генерацию за других**: явно указывать в системном промпте, что ответ модели должен начинаться с определенной команды.
- **Smart Triggers (система смарт-триггеров)**: агент ожидает события (сообщение, `@tag`, смерть/убийство) → немедленный запуск. При таймауте (~10–15 сек) запускается с инструкцией реагировать на общую ситуацию.
- **Выбор модели**:
  - `Mistral NeMo (12B)` + `Saiga NeMo` (русский файн-тюн): наиболее стабильны для ролевой игры, генерации команд и чата.
  - `Qwen 3.5`: показала низкие результаты на сложных промптах.
  - `IBM small models / Mamba`: перспективны для большого контекста и хорошей генерализации.
  - Диффузионные трансформеры: пока не демонстрируют практического превосходства над классическими авторегрессионными LLM.
- **Смена модели**: через `LiteLLM` достаточно изменить имя модели в `.env` и указать API-ключ провайдера. Код менять не требуется.
- **RAG**: механизм поиска и подгрузки определений сленговых/новых слов в контекст для корректного понимания LLM.
- **Идеи (Ideas)**: рандомные подсказки/задачи, внедряемые в промпт для разнообразия поведения в тишине. Выявлена проблема повторения → требуется механизм отслеживания использованных.
- **Ранг игрока**: динамический параметр в БД, зависит от оценок LLM (лайк/дизлайк, выставляемые через тулы).

## 6. Инструменты агента (Agent Tools)
- **Назначение**: набор функций, вызываемых LLM программно для взаимодействия с окружением.
- **`Base Tools / Speak Tool`**: базовый инструмент вывода речи. Содержит поля `комментарий` и `эмоция`. Модель всегда возвращает эмоцию при ответе.
- **`Yandere Mode`**: режим смены персональности/поведения. Активация:
  1. Команда `!Enter Yandere Mode` (обязательно с восклицательным знаком).
  2. В `Speak Tool` поле `эмоция` = `Yandere` (секретная эмоция, прописанная в системной инструкции).
- **Разработка инструментов**: docstring/комментарии в Python-коде автоматически копируются в контекст агента как описание. Обязательно писать подробные комментарии прямо в коде — они станут инструкцией для LLM.
- **Команды/Тулы (сокращения для экономии токенов)**: `!спик` (отправка сообщения), `save user info` (обновление данных), `wait` (ожидание, технически не реализована, но LLM продолжает генерировать).
- **Архитектурные компоненты**: `Reaction Agent` (реакция на события) и `Planner Agent` (планирование/управление триггерами).

## 7. Практические инструкции: запуск, отладка, масштабирование
- **Запуск Java-части (Minecraft)**:
  1. Клонировать репозиторий.
  2. Открыть в VS Code (IDE предложит установить Java-расширения).
  3. `cd <путь_к_проекту>` → `gradle runclient`.
  4. После правок кода достаточно повторно запустить `gradle runclient`.
- **Запуск сервисов (Фильтр + TTS)**: `cd docker/docker-фильтр` → `docker-compose up`. Поднимает контейнеры фильтра и TTS-сервера.
- **Настройка окружения**:
  - Файл промптов: `resources/personalities.uml`.
  - Конфигурация ника: файл `.env`.
- **Взаимодействие в Minecraft (демо)**: командный блок + рычаг → включение полета. Двойное нажатие `Пробел` или `/fly` (права выдаются через консоль/админ-панель).
- **Отладка и профилирование**:
  - Использовать Python debugger, ставить `breakpoint` после инициализации.
  - Запускать локальный сервер для изоляции от внешних ботов и отслеживания триггеров.
  - Расставлять тайминги на этапах выполнения для выявления задержек (сборка промпта ~1 сек на операции с БД и фильтрами).
- **Масштабирование и порты**:
  - 1 клиент Minecraft = 4 порта (Java-сервер + callback, Python-сервер + callback).
  - Для второго клиента: выделить 4 новых порта, создать отдельный `MindBridge 2` или расширить общий для мультиплексирования.
  - Виртуализация: Docker (требует проброса графики), VirtualBox.
- **Git**: `git checkout [хеш/ветка]` для отката к предыдущему коммиту.
- **Рекомендация по архитектуре**: для автономных агентов предпочтительнее писать собственный пайплайн (класс с методом `run`), так как LangChain/LangGraph сложны для кастомизации внутренних циклов и парсинга `tool calls`.

## 8. Задания и рекомендации студентам
- **Предварительное задание**: заполнить форму с детальным описанием персонажа (характер, внешность, предпочтения, психологический тип) для внесения в промпт.
- **Практика в рамках воркшопа**: клонировать репозиторий, отредактировать `personalities.uml` и `.env`, запустить проект через `gradle runclient`, при необходимости модифицировать Java-задачи с помощью AI-ассистентов.
- **К следующему занятию**: подготовить baseline-часть (запустить базовую версию ИИ-стримерши, внести минимальные изменения в промпт). Быть готовыми к подключению к серверам или работе с агентом.
- **Опционально**: самостоятельно запустить Docker-контейнер с фильтром для ознакомления.
- **Общие рекомендации**: погружаться в код проекта, использовать отладчик для разбора логики, задавать вопросы. Акцент сделан на понимании архитектурных компромиссов и практическом изучении структуры.
