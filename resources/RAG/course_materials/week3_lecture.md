## Теория

### Система памяти агента (база данных)

Агент хранит информацию о пользователях в базе данных. В текущей реализации — SQLite (файл `data/natyan_database.sqlite`), в новой версии — Postgres (логика та же).

**Структура данных пользователя:**
- **nick** — игровой ник
- **summary** — текстовое описание игрока, составленное LLM (примеры из базы: «агрессивный соевый мальчик», «пубертатник»). LLM сама решает, как охарактеризовать игрока
- **rank** — числовой рейтинг игрока (от 1 до 5), влияет на отношение агента

**Просмотр базы:** скачать DB Browser for SQLite, открыть файл базы → таблица `users` → столбцы nick и summary.

**Код базы данных:** модуль `database.py` содержит все методы обращения к базе. Класс базы инициализируется при старте и передаётся в инструменты (tools) через `ToolConfig`.

### Механизм сохранения информации о пользователях

**SaveUserInfoTool** — инструмент, который вызывает LLM, когда считает нужным запомнить что-то о пользователе. LLM передаёт ник и текстовое описание, которое сохраняется в поле summary базы данных.

**Like Tool** — простой инструмент для повышения ранга пользователя. LLM вызывает `like(nick)`, происходит обращение к базе: получить текущий rank → rank + 1 → сохранить. Ранг ограничен (максимум 5, минимум 1). Аналогично существует механизм понижения ранга.

Summary и rank передаются в промпт при каждой сборке (prompt constructor) — агент «помнит» всех пользователей, с которыми взаимодействовал.

### Три части агента (детализация)

1. **Сборка промпта (Prompt Constructor)** — папка `prompt_generation/`, файл prompt_constructor. Собирает всю информацию: личность, список игроков с summary из БД, текущие события, описания инструментов
2. **Цикл агента** — метод `step()` в core-агенте, выполняется как `while True`. Каждый шаг: ожидание триггера → сборка промпта → вызов LLM → парсинг ответа → выполнение инструментов
3. **Инструменты (Tools)** — Python-функции в папке `tools/`. ResponseParser (в ToolExecutor в старой архитектуре) парсит вывод LLM и вызывает соответствующие функции

### Tool Status — динамическое описание инструментов

Для инструментов с переменным контекстом (например, Minecraft-команды зависят от сервера) создаётся метод `{tool_name}_tool_status()`. Этот метод автоматически вызывается при каждой сборке промпта и возвращает актуальное описание: на каком сервере агент, какие команды доступны.

Существует база серверов Minecraft с описаниями (выживание, мини-игры и т.д.), чтобы агент понимал контекст каждого сервера. Потенциально можно автоматизировать переходы между серверами.

### Рекомендуемые LLM

Для pipeline стримерши рекомендуются две модели (обе основаны на Mistral Nemo):
1. **CyaNemo Remix i1** — лучший вариант
2. **Saiga Nemo** — второй вариант, форк Mistral Nemo

Обе модели 12B параметров, в квантизации Q4 весят ~7 ГБ. Хорошо держат роль стримерши, работают с обоими pipeline (core-agent и chat-agent).

**Qwen (все версии)** — плохо работают на pipeline стримерши. Часто выдают бессмыслицу, не следуют формату инструментов. Даже «разлоченные» (uncensored) версии Qwen с Hugging Face работают хуже: теряют в агентных способностях, становятся «скучнее» — возможно, нарушается качество при неквалифицированном снятии цензуры.

**Gemma 3** — интересный случай: в обычном чате цензурирована, но на pipeline стримерши самопроизвольно расцензурируется (начинает материться). Предполагаемая причина: игровой контекст + большой промпт + множество инструментов создают ситуацию, выходящую за пределы обучения на безопасность.

### Производительность LLM: Mac M4 vs GPU

Для CyaNemo (12B, Q4):
- **Mac M4** — генерация ~110 токенов/сек (быстрее GPU!), но prompt processing медленнее из-за особенностей объединённой памяти
- **Nvidia 3090** — генерация ~70 токенов/сек, prompt processing ~3400 токенов
- **Nvidia 4090** — prompt processing ~11000 токенов (в 2-3 раза быстрее 3090), генерация ~80-90 токенов/сек

Mac M4 (16 ГБ+) — отличное решение для запуска LLM-части pipeline: быстрая генерация, достаточная память. Оптимальная конфигурация: LLM на Mac, всё остальное (TTS, Minecraft, OBS) на основном ПК.

**Важно:** TTS (Fish Speech) не запускается нормально на Mac — использует кастомные CUDA-ядра. STT тоже заточен под CUDA. Для Mac есть альтернативы: Simple TTS Server (плохое качество, нет интонаций), Kokoro (не тестировался).

Для выноса LLM на Mac: в .env заменить `localhost` на локальный IP Mac'а в сети. LLM запускается через LM Studio или аналог.

### Хак «Focus» — принудительное начало ответа

Проблема: слабые LLM вместо ответа от имени персонажа начинают «продолжать чат» — пишут новые ники, генерируют чужие сообщения, продолжают промпт вместо ответа на него.

**Решение:** в промпт добавляется незаконченное сообщение от имени агента. Добавляется ещё одно сообщение с ролью `assistant`, начинающееся с команды `focus` — «сфокусироваться на ответах юзерам, комментировании ситуаций». LLM видит это как уже начатый ответ и продолжает его, вместо того чтобы генерировать чужие сообщения.

Дополнительно: «не пиши привет» — потому что LLM постоянно начинала каждый ответ с приветствия.

**Это глобальный лайфхак (техника prefill):**
- Работает с большинством локальных LLM
- Не работает с API-моделями (зависит от провайдера)
- Не работает с reasoning-LLM (нужно имитировать reasoning-блок)
- Можно использовать для любого агентного приложения: «Сейчас заполню анализ:» → LLM вынуждена заполнить анализ
- Позволяет жёстко контролировать формат ответа

### Fine-tuning и RL для стримерши

**Текущий статус:** fine-tuning для стримерши ни разу не делался. Идеально фантюнить: на формат ответов (командный формат инструментов) и на личность.

**Идея RL в реальном времени:** зрители стрима дают обратную связь (лайк/дизлайк), LLM обучается в процессе. Эксперимент провалился — модель скатывалась к генерации одной буквы «а-а-а-а» или полной бессмыслице.

**Причины сложности RL:**
- Одновременный инференс + обучение — противоречивые процессы
- Нельзя использовать GGUF (квантизованные модели) — нужны SafeTensors
- Обучение через Transformers/vLLM — медленнее, больше памяти
- Backpropagation через всю модель — огромная нагрузка
- RL сам по себе — тонкий, длительный процесс (недели/месяцы)

**Рекомендация:** начинать с минимального прототипа (кнопки +/-), проверить на маленькой модели, только потом масштабировать.

**Сбор данных для будущего fine-tuning:** добавлена система сохранения в JSON для формирования датасета.

### RAG для актуальной лексики

В pipeline встроен RAG, подмешивающий модные словечки в контекст агента. Если установлена соответствующая LLM (LM Studio), RAG автоматически подключается и обогащает словарный запас стримерши актуальным сленгом.

## Практика

### Просмотр базы данных агента

1. Скачать DB Browser for SQLite
2. Открыть файл `data/natyan_database.sqlite` (или аналогичный для вашего персонажа)
3. Таблица `users` — посмотреть, какие summary LLM сохранила о игроках

### Создание нового инструмента

1. Создать Python-функцию в папке `tools/`
2. Написать говорящее название и подробный docstring (будет скопирован агенту)
3. Если инструменту нужен динамический контекст — создать метод `{имя}_tool_status()` рядом
4. Если инструмент работает с базой — импортировать db из ToolConfig

### Вынос LLM на Mac

1. Установить LM Studio на Mac
2. Загрузить CyaNemo Remix i1 (Q4 квантизация)
3. Запустить сервер в LM Studio
4. В .env на основном ПК заменить `localhost` на IP Mac'а в локальной сети
5. LLM будет работать по сети, всё остальное — локально на ПК

### Вынос TTS на удалённый сервер

Можно перенести TTS на выделенный сервер: в endpoint TTS указать домен (например, `agcraft.ru`), открыть порты. TTS будет работать удалённо, уменьшая нагрузку на локальный ПК.

## Инструменты и технологии

- **SQLite / Postgres** — база данных для хранения информации о пользователях (summary, rank)
- **DB Browser for SQLite** — утилита для просмотра содержимого базы
- **CyaNemo Remix i1** — рекомендуемая LLM для pipeline стримерши (12B, Mistral Nemo-based)
- **Saiga Nemo** — альтернативная рекомендуемая LLM (12B, Mistral Nemo fork)
- **LM Studio** — приложение для запуска локальных LLM (поддерживает GGUF, Mac M-чипы)
- **Simple TTS Server** — простой TTS для Mac (низкое качество, без интонаций)
- **Kokoro** — альтернативный TTS, потенциально работает на Mac
- **Faster Whisper** — STT-система, используемая в pipeline (папка `data_collectors/stt/`)

## Ответы на вопросы студентов

**В: Какая модель используется для управления агентом сейчас?**
О: CyaNemo Remix i1, развёрнутая локально на Mac M4 и доступная через локальную сеть.

**В: Какие характеристики Mac нужны для нормальной работы?**
О: Mac M4 с 16+ ГБ памяти. Модель 12B в Q4 квантизации весит ~7 ГБ. Генерация быстрее, чем на 3090 (110 vs 70 токенов/сек), но prompt processing медленнее.

**В: Думал ли ты fine-tuning'ить LLM на конкретный характер?**
О: Давно хочу, но не дошли руки. Идеально fine-tuning'ить на формат ответов и на личность. Началась работа по сбору данных в JSON для формирования датасета. RL в реальном времени пробовал — провалился (модель скатывается в бессмыслицу).

**В: Какой TTS можно использовать на Mac?**
О: Fish Speech плохо работает на Mac (CUDA-зависимость). Альтернативы: Simple TTS Server (низкое качество), Kokoro (не тестировался). Лучший вариант — вынести TTS на сервер или ПК с CUDA GPU.

**В: Почему зацензурированные LLM расцензурируются на pipeline стримерши?**
О: Предполагаемые причины: игровой контекст выводит LLM за пределы обучения на безопасность; большой промпт с множеством инструментов; LLM «думает», что в игре можно больше, чем в чат-боте. Особенно заметно на Gemma 3.
