## Часть I. Память агента

**1.** Что записывает LLM в поле `summary` базы данных пользователей?

а) Сжатую копию последних N реплик игрока
б) JSON со счётчиками сообщений и временем активности
в) Список игровых статистик: HP, инвентарь, координаты
г) Свободную текстовую характеристику игрока (например, «агрессивный соевый мальчик»)

**2.** Что обозначает столбец `rank` в таблице пользователей?

а) Длину текста summary в символах
б) Порядок появления игрока на сервере
в) Числовой рейтинг отношения агента к игроку (в проекте — от 1 до 5)
г) Уникальный numeric id строки в таблице

**3.** Каким образом база пополняется новой информацией про игрока?

а) Автоматически — раз в 5 минут парсер чата проходит по логам
б) LLM решает запомнить факт и явно вызывает инструмент сохранения
в) Админ заполняет вручную через веб-форму
г) При первом подключении пишутся дефолты, дальше БД не меняется

**4.** Какую задачу решает инструмент `SaveUserInfoTool`?

а) Сохраняет в БД текстовое описание игрока, переданное LLM
б) Архивирует summary в zip-файл раз в сутки
в) Отправляет уведомление модератору о новом игроке
г) Сбрасывает поле `summary` обратно в пустую строку

**5.** Что делает Like Tool, когда LLM вызывает `like(nick)`?

а) Перезаписывает summary новой положительной фразой
б) Ставит лайк на видеостриминг-платформе через API
в) Создаёт новую запись в отдельной таблице `likes`
г) Прибавляет 1 к `rank` соответствующего пользователя (в пределах верхней границы)

**6.** Может ли `rank` бесконечно расти при многократных лайках?

а) Да, ограничений нет — это произвольный integer
б) Растёт, но с экспоненциальным замедлением
в) Нет, ранг ограничен сверху небольшим числом (в курсе — 5)
г) Растёт, пока LLM не вызовет специальный сброс

**7.** В какой момент `summary` и `rank` всех знакомых пользователей оказываются доступны агенту?

а) Только когда юзер пишет — выгружается только его профиль
б) При каждой сборке промпта prompt-constructor подмешивает их в контекст
в) Через долгий vector-search в RAG
г) Никогда — БД пишется на запись и не читается во время сессии

**8.** Какая база данных используется для хранения пользовательских профилей агента в текущей реализации?

а) SQLite-файл (в новой версии — Postgres, логика та же)
б) ChromaDB как векторная база
в) Plain text JSON-файл в корне проекта
г) Etcd в Kubernetes-кластере

**9.** Чем удобно смотреть, что агент запомнил о игроках?

а) Через REST-эндпоинт `/api/users/all`
б) `journalctl -u agent.service` в Linux
в) Файл `summary_dump.log` в каталоге `data/logs/`
г) DB Browser for SQLite, таблица `users`

**10.** Как именно tools получают handle на базу данных?

а) Каждый tool делает `sqlite3.connect()` при вызове
б) Через переменные окружения, читаемые внутри функции
в) База передаётся в tools через объект `ToolConfig` при инициализации
г) Tools не работают с БД напрямую — только через отдельный микросервис

**11.** Что представляет собой `UserInfo` в коде агента?

а) Запись в файле `.env` с параметрами текущего игрока
б) Структура, агрегирующая данные из БД и игровые метрики игрока; поддерживает привязку нескольких ников к одному профилю
в) Метод Python для логирования действий пользователя в файл
г) Таблица в Postgres с настройками текущего Minecraft-сервера

**12.** Какое из утверждений про память агента в курсе НЕВЕРНО?

а) Pipeline хранит полную историю всех сообщений каждого игрока
б) summary пишется LLM свободным текстом
в) Агент видит summary и rank всех известных игроков в каждом промпте
г) Like-инструмент увеличивает rank в пределах разрешённого диапазона

## Часть II. Система инструментов (Tool system)

**13.** В каком виде существуют инструменты агента в коде проекта?

а) Записи в YAML с описанием параметров и возвращаемых значений
б) Plugin'ы для LM Studio с собственным форматом манифеста
в) Контейнеры Docker, которые агент дёргает по HTTP
г) Обычные Python-функции в выделенной папке с инструментами

**14.** Где LLM видит описание того, что делает каждый инструмент?

а) В комментариях `# tool: ...` над функцией
б) В отдельном MD-файле, который кэшируется при старте
в) В docstring соответствующей Python-функции — он копируется в промпт
г) В таблице `tool_descriptions` в базе данных

**15.** Какие действия выполняет инструмент `speak`?

а) Только TTS, текст в чат уходит через отдельный канал
б) Одновременно отправляет фразу в TTS и в игровой чат
в) Сохраняет фразу как голосовое сообщение в БД
г) Воспроизводит звук уведомления без синтеза речи

**16.** Какова роль параметра `emotion` в `speak`?

а) Меняет окраску синтеза речи и может переключить вариант голоса
б) Кодирует фразу для шифрованной отправки на сервер стриминга
в) Прибавляет очки модератору в админ-панели
г) Никак не используется — оставлен для совместимости

**17.** Что возвращает `{tool_name}_tool_status()`?

а) `True`/`False` — проверка готовности инструмента
б) Случайный seed для генерации варианта поведения
в) Время последнего вызова в Unix-timestamp
г) Текстовое описание текущего контекста инструмента (например, на каком сервере агент и какие команды доступны)

**18.** Когда срабатывает `tool_status`?

а) После каждой смерти агента в игре
б) Только при вызове ответственного tool'а
в) При каждой пересборке промпта агента
г) При старте pipeline один раз — потом данные кешируются

**19.** Кто разбирает вывод LLM на «вот тут вызов tool, а вот тут речь»?

а) Сама модель возвращает строгий JSON, парсить не нужно
б) Внутри pipeline есть ResponseParser/ToolExecutor, который ищет команды в тексте и вызывает функции
в) Регулярное выражение в Java-моде Minecraft
г) LM Studio выделяет вызовы tools и подаёт их отдельно

**20.** Что такое prefill (Focus-хак) для LLM в этом курсе?

а) Префиксная фраза в начале сообщения ассистента, которую LLM обязана продолжить — задаёт формат и тему ответа
б) Метод сжатия контекста перед отправкой в модель
в) Дополнительный системный промпт, добавляемый в середину диалога
г) Способ обойти rate-limit платных API через очередь

**21.** Где prefill не сработает или сработает плохо?

а) В локальных LLM, работающих через LM Studio
б) В моделях, дообученных через LoRA
в) В моделях с маленьким контекстом (до 4k)
г) В большинстве API-провайдеров (которые не отдают control над началом ответа) и в reasoning-моделях

**22.** Чем компактный командный формат tool-вызовов (типа `strike nick`) лучше для слабых LLM, чем JSON-формат function calling?

а) JSON в pipeline вообще запрещён лицензией LLM
б) Командный формат поддерживает картинки и видео
в) Командный формат компактнее JSON и обеспечивает более быструю реакцию агента
г) Командный формат шифруется автоматически

**23.** Какие шаги нужны, чтобы добавить в агента новый инструмент с контекст-зависимым поведением?

а) Зарегистрировать tool через CLI-команду `tools add`
б) Дописать функцию с docstring и добавить рядом `{name}_tool_status()` для динамического описания
в) Прописать tool в общий JSON-манифест и перезапустить pipeline
г) Достаточно положить файл `.tool` в каталог inbox — остальное pipeline сделает сам

**24.** По какой причине в курсе для агента не взяли LangChain / LangGraph / SmolAgents, а написали свой pipeline?

а) Все эти фреймворки рассчитаны на задачи с финальным результатом, а не на бесконечный цикл агента; кастомизация под автономный pipeline превращается в боль
б) Они не работают с локальными моделями GGUF
в) У них нет поддержки Linux-серверов
г) Авторы курса не знают этих фреймворков
