## Часть I. Память агента

**1.** Что именно хранится в поле `summary` в базе данных агента про каждого пользователя?

а) Хеш последних 50 сообщений пользователя
б) Список всех команд, которые пользователь вызывал в чате
в) Текстовая характеристика, составленная LLM (например: «агрессивный соевый мальчик»)
г) Эмбеддинг профиля для семантического поиска

**2.** Чем по своей природе различаются поля `summary` и `rank`?

а) Они идентичны по типу, отличаются только именем колонки
б) Summary публичное, rank скрытое от агента
в) Summary — массив тегов, rank — взвешенная сумма этих тегов
г) Summary — строка свободной формы, rank — целое число в фиксированном диапазоне

**3.** Кто принимает решение, что именно записать в `summary` игрока?

а) Языковая модель сама — через вызов специального инструмента
б) Серверный модератор вручную в админ-панели
в) Регулярные выражения, ищущие заранее заданные паттерны в чате
г) Pipeline автоматически, раз в N сообщений, по фиксированному шаблону

**4.** Что делает инструмент `SaveUserInfoTool`?

а) Делает дамп всей оперативной памяти агента в файл
б) Записывает текстовое описание пользователя в поле `summary` базы
в) Создаёт резервную копию базы данных перед остановкой агента
г) Шифрует summary, чтобы только агент мог его прочитать

**5.** Что делает инструмент `Like` (или его аналог `like(nick)`)?

а) Отправляет реакцию-сердечко в чат стрима
б) Помечает summary как «проверенное» и блокирует его перезапись
в) Увеличивает поле `rank` на 1 в пределах допустимого диапазона
г) Сохраняет timestamp последнего одобрительного действия

**6.** В каком диапазоне ограничен ранг игрока в реализации курса?

а) От 1 до 5 включительно
б) От 0 до 100 с шагом 5
в) Не ограничен — растёт, пока LLM поднимает
г) От -10 до +10 с нейтралью в нуле

**7.** Как `summary` и `rank` знакомых пользователей попадают в контекст агента?

а) Только при явной команде `recall <nick>` в чате
б) Передаются один раз при старте сессии и больше не обновляются
в) Хранятся отдельно и подгружаются только через RAG-запрос
г) Подмешиваются в промпт при каждой его сборке для всех знакомых пользователей

**8.** На какой технологии хранится база пользователей в текущей реализации?

а) Redis с TTL на каждую запись
б) Файл SQLite в каталоге `data/` (в новой версии — Postgres, логика та же)
в) MongoDB с одной коллекцией на каждого пользователя
г) Плоский YAML, перечитываемый каждые 10 секунд

**9.** Какой утилитой курс предлагает смотреть содержимое базы?

а) Встроенная веб-админка на порту 8080
б) Расширение VS Code «SQLite Explorer»
в) Через прямые SQL-запросы в терминале без сторонних программ
г) DB Browser for SQLite — открыть файл базы, таблица `users`

**10.** Как инструменты получают доступ к базе данных в pipeline?

а) База инициализируется при старте и передаётся в tools через `ToolConfig`
б) Каждый tool открывает свой коннект при первом вызове
в) Через глобальную переменную модуля, импортируемую в каждый tool
г) Через REST-эндпоинт на localhost, который инструменты дёргают по HTTP

**11.** Что такое `UserInfo` в архитектуре агента?

а) Алиас для таблицы `users` в SQLite-базе
б) Базовый класс, от которого наследуются все Python-инструменты
в) Структура данных об игроке: агрегирует данные из БД, поддерживает привязку нескольких ников, хранит игровые метрики
г) Класс, выполняющий парсинг чата по никнеймам

**12.** Что из перечисленного НЕ хранится в БД агента про каждого пользователя?

а) Текстовая характеристика, написанная LLM
б) Полная история всех сообщений и голосовых пакетов от него
в) Игровой ник
г) Численный ранг отношения

## Часть II. Система инструментов (Tool system)

**13.** Чем физически является инструмент агента в коде проекта?

а) Python-функция в выделенной папке (например, `tools/` или `agent_tools/`)
б) JSON-описание схемы в конфиге, исполняемое внешним сервисом
в) Запись в базе данных с SQL-кодом, который агент выполняет
г) Bash-скрипт, который агент запускает через subprocess

**14.** Откуда берётся описание инструмента, которое видит LLM в промпте?

а) Поле `description` в отдельном YAML-файле для каждого tool
б) Автоматически сгенерированный текст по сигнатуре функции
в) Вручную написанный текст в общем файле `tools_manifest.json`
г) Docstring (строка-комментарий) самой Python-функции — он копируется в промпт

**15.** Какое поведение реализует базовый инструмент `speak`?

а) Только синтез речи через TTS, без вывода в чат
б) И отправку в TTS, и параллельный вывод в чат Minecraft
в) Только сообщение в чат Minecraft, без TTS
г) Запись фразы в лог-файл с пометкой «озвучено»

**16.** Зачем у `speak` параметр `emotion`?

а) Сохраняется в БД как часть summary говорящего
б) Управляет цветом подсветки сообщения в OBS-оверлее
в) Влияет на интонацию озвучки и может переключать вариант голоса
г) Используется как seed для генерации текста ответа

**17.** Что такое `{tool_name}_tool_status()` в проекте?

а) Метод, возвращающий динамическое описание инструмента в зависимости от контекста (например, какие команды доступны на текущем сервере)
б) Простой ping для проверки, что инструмент жив
в) Логгер, пишущий в файл каждый вызов инструмента
г) Запрос в БД для подсчёта числа вызовов tool'а за сессию

**18.** Когда вызывается `tool_status`-метод инструмента?

а) Один раз при старте агента, дальше кешируется
б) Раз в минуту по расписанию, независимо от состояния агента
в) Только когда LLM явно запрашивает «обнови tools»
г) При каждом построении промпта — чтобы агент видел актуальный контекст

**19.** Кто и как разбирает ответ LLM, чтобы понять, какой tool вызвать?

а) Сама LLM возвращает строгий JSON, который исполняется напрямую
б) Парсинг делается на стороне LM Studio до того, как ответ дойдёт до агента
в) В pipeline есть ResponseParser/ToolExecutor — он разбирает текст ответа и вызывает функцию
г) Внешний сервис на Java принимает поток текста и вызывает Python-функции по сети

**20.** В чём смысл хака «prefill» (он же «focus») в курсе?

а) Скачивать веса модели заранее, чтобы первый ответ был быстрее
б) Заранее «начинать» ответ ассистента префиксом, который LLM продолжит, — это жёстко задаёт формат и тему
в) Прогревать видеокарту до целевой температуры перед сессией
г) Запрашивать у LLM план до основного ответа, как chain-of-thought

**21.** Где prefill НЕ работает или работает плохо?

а) На большинстве API-моделей и на reasoning-моделях
б) На локальных LLM в LM Studio
в) На квантизованных моделях форматов GGUF
г) На моделях с контекстом длиннее 16k токенов

**22.** Какое преимущество компактного командного формата вызова инструментов перед JSON авторы курса называют главным?

а) Поддержка эмодзи и кириллицы в именах функций
б) Возможность шифровать вызовы с помощью встроенных средств LLM
в) Совместимость с любым браузером без дополнительных библиотек
г) Командный формат компактнее JSON и позволяет агенту быстрее реагировать

**23.** Что нужно сделать, чтобы добавить новый tool с динамическим контекстом?

а) Только зарегистрировать функцию в `tools_manifest.json`
б) Дописать новый case в большой `switch`-блок ResponseParser'а
в) Создать Python-функцию с говорящим docstring и метод `{имя}_tool_status()` для динамики
г) Перекомпилировать pipeline после `gradle build`

**24.** Почему авторы курса не используют LangChain / LangGraph / SmolAgents как базу для своего агента?

а) У них нет поддержки русскоязычных моделей
б) Эти фреймворки заточены под задачи с конечным результатом, а не под бесконечный цикл while-true автономного агента
в) Они платные и требуют корпоративную лицензию
г) Они не работают на Windows
