## UserInfo — структура «всё что агент знает о пользователе»

UserInfo — это структура данных об одном игроке (пользователе), которую агент собирает каждый раз, когда нужно ответить или принять решение про этого человека. Не путать с просто «строкой в БД»: UserInfo — это **агрегированный объект**, который объединяет несколько источников.

**Что входит в UserInfo:**

- Привязка нескольких ников к одному пользователю (если человек играл с разных аккаунтов, его можно объединить под одной UserInfo).
- Данные из БД: summary (текстовая характеристика, что говорил/делал) и rank (число 1-5, отношение агента к пользователю).
- Статистика упоминаний этого пользователя другими.
- Игровые метрики в реальном времени: HP, режим (выживание/креатив), позиция в мире, предмет в руках, возможность атаки.

**Зачем нужно объединение:** одиночное поле БД не даёт LLM полной картины. Чтобы агент решил «прыгать ли на этого человека», нужны и текстовое summary (был ли он раньше враждебен), и rank (как агент к нему сейчас относится), и игровые метрики (есть ли у него оружие). UserInfo — это сборка всего этого в один объект.

**Где используется:** Prompt Constructor берёт UserInfo по нику говорящего и подставляет в сборку промпта перед каждым ответом LLM.

## Командный формат инструментов vs JSON

Стандартный подход в большинстве агентных фреймворков (LangChain, OpenAI function calling) — это JSON-формат вызова инструментов. LLM генерирует JSON-объект с полями `name` и `arguments`, фреймворк его парсит и вызывает функцию.

В этом проекте используется другой подход — **командный формат**. LLM пишет вызов инструмента как строку команды, по типу bash-команды или slash-команды в чате:

```
strike nick
save-user-info!
speak комментарий
like nick
```

Каждый инструмент — это обычная Python-функция в папке `tools/`. Её docstring автоматически копируется в промпт как описание для LLM.

**Почему командный формат лучше JSON для этого случая:**

1. **Компактнее.** JSON-вызов требует кавычек, фигурных скобок, явных названий полей. Командная строка `strike nick` — это два слова. Меньше токенов в промпте и в ответе LLM → меньше задержка, меньше расход контекста.

2. **Быстрее реагирует.** Меньше токенов на генерацию → раньше получаем готовую команду из stream'а. Для реактивного агента, который должен среагировать на событие в Minecraft за секунды, это критично.

3. **Проще парсить.** ResponseParser работает регулярками и split'ом строки. JSON-парсер ломается на любой невалидной кавычке от LLM (а слабые модели регулярно её ставят).

4. **Привычнее для LLM.** Игровые/чатовые модели видели в обучающем корпусе много slash-команд (Discord, Twitch, Minecraft). JSON tool_calls — это технический формат, на нём обучены преимущественно instruct-модели от больших провайдеров.

5. **Не требует fine-tuning.** SmolAgents предлагает альтернативу — LLM пишет Python-код вызова. Но без fine-tuning модели начинают писать сложный код вместо простого вызова (циклы, новые функции на 100 строк). Командный формат остаётся простым и понятным без дополнительного обучения.

**Минус командного формата:** для каждой команды нужен свой парсер аргументов. Но в pipeline стримерши команд десятки, не сотни, и однотипные — это терпимая цена за остальные плюсы.

## prefill и Focus — приёмы для системы инструментов

Когда LLM используется как агент, который должен **выбирать инструменты и вызывать их в правильном формате**, слабые модели регулярно ошибаются: вместо вызова инструмента продолжают чужой диалог, начинают новую реплику от другого ника, выдают пустой ответ. Чтобы заставить такую LLM именно реагировать как агент (с командой инструмента в начале), используют две связанные техники: **prefill** и хак **«Focus»**.

**prefill (предзаполнение ответа):** в API многих LLM можно передать начало ответа как уже сказанное ассистентом. LLM получает промпт + «уже начатый» ответ, и её задача — продолжить с этого места. Это глобальный приём, не специфический для этого проекта.

Пример. Без prefill агент получает только промпт и может ответить пустотой или копией чужой реплики. С prefill в качестве «начала ответа» подставляется строка типа `agent_nick: ` или начало нужной tool-команды (`speak ` или `like `). LLM видит уже начатый ответ от имени агента и продолжает в нужном формате.

**Хак «Focus»:** конкретное применение prefill в pipeline стримерши. Когда нужно гарантированно начать ответ командой инструмента, в prefill подсовывают начало команды. LLM «фокусируется» именно на завершении этой команды, а не свободно генерирует.

**Связь с системой инструментов:** командный формат инструментов и prefill работают в паре. Командный формат компактный — для prefill достаточно подсунуть 1-2 слова (`speak `), и LLM выдаёт остаток. С JSON-форматом prefill сложнее: нужно подсовывать частичный JSON-объект, что LLM путает.

**Ограничения prefill:**
- НЕ работает на API-моделях большинства провайдеров (OpenAI, Anthropic, Google) — у них в API нет поля «начало ответа ассистента», prefill блокируется по соображениям безопасности.
- НЕ работает на reasoning-моделях (o1, o3, gpt-5 reasoning, DeepSeek R1) — у них собственный внутренний reasoning, который prefill ломает.
- Работает с большинством локальных LLM, которые запускаются через стандартный inference (llama.cpp, vLLM, transformers).

**Вывод:** prefill — это не про память агента, и не про определение инструмента как Python-функции. Это **исполнительный приём**, который заставляет LLM реально пользоваться системой инструментов, а не игнорировать её. Без prefill слабые локальные модели в pipeline стримерши работали бы плохо.
