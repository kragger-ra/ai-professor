## 1. Архитектура агента и пайплайн
- **Одноагентная (Single-Agent) vs мультиагентная архитектура:** Выбрана одноагентная для устранения рассинхрона контекста (в мультиагентной game- и chat-агенты не знают о действиях друг друга). Минусы: высокая нагрузка на контекстное окно, снижение скорости, сложность оптимизации.
- **Основные компоненты:** 
  - `Prompt Generation` — конструктор, агрегирующий контекст (данные об играх, пользователях, статусах инструментов).
  - `Agent Loop` — основной цикл выполнения (`while true`).
  - `Tools` — функции для внешних действий.
  - `Trigger` — механизм задержки/активации цикла, влияет на выбор сообщения для ответа.
  - `Response Parser` — вынесен из `tool executor` в отдельный модуль (в старых версиях может быть внутри).
- **Пайплайн синхронизации:** Последовательность сервисов, обеспечивающая согласованную работу компонентов и обработку входящих событий из соцсетей/чатов в общий контекст.
- **Динамическая структура:** Последовательная загрузка/выгрузка моделей под задачи (например, `Video-LLM` для анализа → `Role-LLM` для отыгрыша) для оптимизации ресурсов.
- **Мультиархитектурность:** Возможность замены базовой LLM одной строкой кода без переписывания логики пайплайна.

## 2. Система памяти и работа с базами данных
- **Механизм памяти:** Фиксация комментариев из чата, формирование кратких сводок (`summary`), влияние на внутреннее состояние/настроение персонажа.
- **Хранилище:** Централизованная БД событий. Старый пайплайн: `SQLite` (`data/hyper.aedatabase.sqlite`), новый: `PostgreSQL`.
- **Взаимодействие:** LLM самостоятельно решает, информацию о каких пользователях сохранять. Инструменты напрямую вызывают методы БД.
- **Инициализация:** БД импортируется в `tool-config`, передаётся при инициализации модуля `tools`. Все обращения инкапсулированы в `database.py`.
- **Просмотр памяти:** Через `DB Browser for SQLite` → открыть файл БД → таблица `users` (поля `nick`, `summary`).

## 3. Выбор, оптимизация и запуск LLM
- **Форматы и квантизация:** Инференс работает в `GGUF` (поддерживает квантизацию, напр. `Q4` ~7 ГБ VRAM для 12B-моделей). Обучение требует полных весов (`SafeTensors`/`Transformers`), на GGUF невозможно.
- **Разделение нагрузки:** Вынос LLM на отдельное устройство (Mac/ноутбук) через `LM Studio`. В `.env` основного проекта заменить `localhost` на локальный IP машины с LM Studio (`192.168.0.x`).
- **Производительность:** 
  - `prompt processing` (первая задержка) vs `token generation` (скорость вывода).
  - Зависит от архитектуры памяти: Mac M4 ~110 ток/с (генерация), RTX 3090 ~70 ток/с. RTX 4090 быстрее обрабатывает промпт (~11K токенов vs ~4K на 3090).
- **Рекомендуемые модели:** `Cynemo Remix i1`, `Saiga` (на базе `Mistral Nemo`, стабильно держат роль стримерши). `Qwen` плохо справляется с ролью в данном пайплайне. `Fred` (1.7B, ~2022 г.) устарела, но эффективна для анализа ников.
- **Ограничения генерации:** `repetition_penalty` (или `ngram_repeat_penalty`) для борьбы с зацикливанием. Повышение `temperature` ломает структуру промпта и парсер команд.
- **Инференс vs Обучение:** Совмещение на одной машине неэффективно: требует ~100 ГБ VRAM, вызывает падение скорости из-за расчёта обратного распространения ошибки.

## 4. Инструменты (Tools) и вызов функций
- **Механизм вызова:** LLM генерирует структуры вызова (JSON или кастомный формат `tool Command` + аргументы). Few-shot примеры в промпте повышают точность, но в автономных сценариях недостаточны.
- **`Tool Status` (`_tool_status`):** Метод, автоматически вызываемый сборщиком промпта для динамического формирования описания инструмента под текущий контекст.
- **Базовые инструменты:** 
  - `speak` — автоматически дублирует вывод в TTS и чат Minecraft (`mc send`).
  - `save user info/summary` — принимает ник и суммаризацию, сохраняет/обновляет запись в БД.
  - `like` — увеличивает ранг пользователя на `+1`. ⚠️ **Баг:** в новой миграции отсутствует проверка на максимум. Требуется ограничение `rank ≤ 5`.
  - `focus` — заглушка-инструмент.
- **Требования:** Названия и описания функций должны быть точными, так как передаются в промпт без дополнительной обработки.

## 5. Промпт-инжиниринг и управление поведением
- **Критическая зависимость:** Качество, скорость и ролевой отыгрыш напрямую определяются промптом. Отсутствие жёстких ограничений ведёт к «деградации» и выходу из роли.
- **Хак предзаполнения (Prompt Continuation Hack):** В историю диалога добавляется незавершённое сообщение ассистента (напр. `анализ: `). LLM вынуждена продолжить генерацию строго с указанной точки. Стабильно работает на локальных open-source без reasoning.
- **Феномен «непроизвольного расцензурирования»:** В агентном пайплайне с игровым контекстом зацензуренные модели (Gemma 3, Qwen) могут терять ограничения. Гипотеза: контекст игры меняет внутреннее восприятие модели, снимая «чат-бот» барьеры.
- **Лексический контекст:** Добавление сленга/модных слов кардинально меняет поведенческие паттерны (риск перехода к деструктивному/подростковому поведению).
- **RAG для сленга:** Векторный поиск по базе (~50 слов/фраз, разбитых на фрагменты по 3 строки в `Documents/Resources/...`). Подставляет релевантные определения в контекст LLM.
- **Спам-защита:** Встроенный механизм блокировки реакции на повторяющиеся запросы.
- **Проактивность:** При отсутствии активности в чате агент должен самостоятельно инициировать сообщение.
- **Этика:** Необходимость внедрения правил поведения (аналог законов робототехники) для контроля автономных персонажей.

## 6. Интеграция с Minecraft и физическая симуляция
- **Среда:** Minecraft (Vanilla, серверы SkyWars, Bedwars, RP-серверы). Интеграция через `Minebridge`/`Mineflayer`.
- **Навигация:** 
  - `Baritone` — стандартный маршрутизатор (блочный, роботизированный).
  - `Tungsten` — кастомный фреймворк физической симуляции (запускает локальную мини-симуляцию с тысячами агентов-кандидатов).
- **Проблемы pathfinding:** Комбинаторика на сложных участках (лестницы, дальние прыжки), «дрифт» при столкновениях, игнорирование ковров, преждевременный обрыв маршрута (>50 блоков алгоритм считает неэффективным).
- **Физическая симуляция:** Просчёт траекторий в реальном времени, баллистический расчёт для лука/трезубца. LLM-модуль отключается во время демонстрации чистой навигации.
- **RP-агент:** Ограничен в понимании пространства/инвентаря, требует хардкода координат ключевых точек (магазины, полиция) и базовых взаимодействий.
- **Команды:** `follow player <ник>`, `Set Warp Idea`, `Warp Idea`, `Game Mode Креатив`. `Hot-swap` — замена модулей на лету. `Telebridge` — алгоритм мостостроения (внешний PR).

## 7. Обработка речи (STT/TTS) и Real-time диалог
- **Архитектурная изоляция:** STT/TTS выносятся в отдельные микросервисы/контейнеры (Docker) для стабильности.
- **STT:** `Whisper` (совместим с Mac), `Faster Whisper` (локально), `Whisper Live Kit` (неудовлетворительно в текущем пайплайне). Требуется поиск быстрого open-source решения (<20 сек).
- **TTS:** `Fish Speech` (требует CUDA, нестабилен на Mac), `Coqui TTS` (удалённый сервер `tts.jkraft.ru`), `Kokoro TTS` (для macOS), `Simple TTS Server` (резерв, низкое качество).
- **Real-time диалог:** Задержка в миллисекунды, возможность перебивания без потери контекста. Требует отдельного сервиса мгновенного анализа. `NVIDIA PersonaPlex` упоминается как готовое решение.

## 8. Контент-стратегия: нарезка клипов и продвижение
- **Миф «Запустил и забыл»:** Автоматизация не гарантирует рост аудитории. Нужна контентная стратегия, регулярное управление и коллаборации.
- **Отложенная нарезка (Delayed clipping):** Оффлайн-анализ записи стрима LLM → поиск виральных моментов/таймкодов → вырезка. Альтернатива real-time нарезке.
- **Pipeline нарезки:** Мониторинг чата → пауза стрима (~10 мин) → LLM-анализ лога → фиксация таймингов → передача в скрипт нарезки → ручная выгрузка (из-за капчи/API ограничений).
- **Каскадная генерация / «угарность»:** Слабая модель/цепь Маркова генерирует шум/теги → основная LLM формирует ответ. Использует «шумность» моделей (напр. `Fred T5`) для комичного эффекта.
- **Реактивный контент:** `Video-LLM` анализирует видео → `Role-LLM` генерирует реакцию от лица персонажа.
- **Метрики:** Частота сообщений, удержание (retention), конверсия просмотров в подписчиков.

## 9. Мультиагентность, ивенты и креативность
- **Мультиагентные дебаты:** Несколько LLM обсуждают задачу, аргументируя позиции друг против друга.
- **Обратный тест Тьюринга:** Ивент, где участники угадывают, кто из собеседников человек, а кто агент.
- **Агент для ивентов:** Чёткая цель/сценарий (дебаты, мини-игры, тесты), в отличие от свободного чата.
- **`IdeaSuggester`:** Модуль генерации идей (`resources/ideas.yaml`). Требует логирования использованных идей, запрета повторов и таймеров задержки (напр. 1 день).
- **Рейды и свита:** Скоординированные действия группы агентов по атаке или взаимодействию.

## 10. Практические инструкции, отладка и методология
- **Настройка сети:** Замена `localhost` на локальный IP в `.env`, открытие портов для удалённых сервисов.
- **Отладка и безопасность:** Отзыв привилегий оператора (`опка`) у ИИ для защиты регионов. Аудит промпта на скрытые инструкции. Документирование инцидентов.
- **Git-воркфлоу:** `Pre-existing bug, read, bash, commit, push.` В демо коммиты идут в `main`, обработка внешних PR.
- **Использование Claude:** Эффективен для анализа больших Java-репозиториев, рефакторинга пайплайна и ускорения вычислений (~в 5 раз).
- **Прототипирование RL:** Начинать с минимального прототипа (кнопки «+»/«-», малая модель). Масштабировать только после стабильной работы.
- **Методология разработки:** Начинать с мини-прототипов, фокусироваться на одном направлении, избегать распыления ресурсов.
